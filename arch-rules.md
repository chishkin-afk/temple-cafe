# Архитектурные правила chishkin-afk

Этот документ описывает наблюдаемый стиль архитектуры публичных репозиториев [chishkin-afk](https://github.com/chishkin-afk). Правила сформулированы по реальному коду, а не по абстрактному шаблону FSD. Дата анализа: **19 октября 2026 года**.

Основной подход: **FSD со слоем `views`, отдельным маршрутизирующим слоем Next.js, прямыми импортами файлов и SCSS Modules**. Организация следует предметным областям и ответственности; дополнительные уровни абстракции появляются по необходимости.

## 1. Основания и границы анализа

Проверен актуальный список публичных репозиториев через GitHub API. Детально изучены структура, конфигурация, характерные компоненты и импорты двух фронтенд-проектов. Три Go-проекта просмотрены для сопоставления архитектурного подхода. Приватные репозитории и история всех веток в анализ не входят.

| Репозиторий | Роль в анализе | Зафиксированный коммит |
| --- | --- | --- |
| [portfolio](https://github.com/chishkin-afk/portfolio) | Основной пример сайта: композиция секций, компактные компоненты, контентные модели | `efd62dddb8776423ec05452e61ac88c3beb9d520` |
| [wehicle-demo](https://github.com/chishkin-afk/wehicle-demo) | Основной пример приложения: формы, рабочие экраны, общее состояние, связи сущностей | `a482de44c0eb4e4d4c5e8ec32bdff77c90df545b` |
| [posted](https://github.com/chishkin-afk/posted) | Контекст: Go, микросервисы, разделение domain/application/infrastructure | `09de922570a477512fbb4243c8241a144bac836a` |
| [weather-ai](https://github.com/chishkin-afk/weather-ai) | Контекст: Go, домены и внешние адаптеры | `a120d48c08f776fcb9ff0a4b9061ca3fb2e45031` |
| [todo](https://github.com/chishkin-afk/todo) | Контекст: Go, предметные модули auth/task с внутренними слоями | `86e79ee55bded1d2b9e52976a4030a2584fdf739` |

Форки `gin`, `go-yaml`, `Practice-Contribution`, `first-contributions` не использованы как доказательство авторского стиля. Репозиторий `aimal3` имеет нулевой размер по API и не даёт материала для анализа FSD.

Далее **общее правило** означает практику, подтверждённую обоими фронтенд-проектами. Особенности одного проекта помечены отдельно. Предложения для нового проекта обозначены как рекомендации, а не как уже существующие авторские требования.

## 2. Слои и ответственность

В обоих фронтенд-проектах есть шесть слоёв:

```text
src/
├── app/          # Next.js: маршруты, layouts, metadata, error/loading boundaries
├── views/        # Страницы приложения и композиция их содержимого
├── widgets/      # Самостоятельные секции и крупные блоки интерфейса
├── features/     # Пользовательские действия и сценарии
├── entities/     # Предметные модели, данные, представления сущностей
└── shared/       # Общий UI, утилиты, конфигурация и стили
```

| Слой | Что сюда относится | Примеры из кода |
| --- | --- | --- |
| `app` | Привязка URL к экрану, корневое окружение, метаданные, подключение провайдеров | `app/page.tsx`, `app/dashboard/layout.tsx` |
| `views` | Полный экран, сборка виджетов и фич, состояние и логика конкретного экрана | `views/home`, `views/bookings`, `views/account` |
| `widgets` | Секция сайта или самостоятельный составной блок | `widgets/hero`, `widgets/projects`, `widgets/app-shell`, `widgets/booking-list` |
| `features` | Завершённое действие пользователя | `features/copy-email`, `features/project-estimate`, `features/booking`, `features/record-editor` |
| `entities` | Предметные данные и их типы; UI сущности, если он нужен | `entities/project`, `entities/service`, `entities/booking` |
| `shared` | Код без привязки к конкретному бизнес-сценарию | `shared/ui/button`, `shared/lib/format`, `shared/config/site` |

**Правила воспроизведения стиля:**

1. Использовать `views` для содержимого страниц, сохраняя `app` для интеграции с Next.js. Отдельного FSD-слоя `pages` в изученных проектах нет.
2. Называть слайсы по смыслу: `project`, `booking`, `copy-email`, `app-shell`.
3. Не складывать весь интерфейс в общие корневые `components`, `hooks` или `utils`: сначала определять владельца кода.
4. Выносить в `shared` действительно общие элементы. Например, карточка проекта остаётся в `entities/project/ui`, а универсальная кнопка — в `shared/ui`.
5. Не превращать любую секцию в feature: `hero` и `footer` — widgets; копирование почты — feature.

## 3. Направление зависимостей

Порядок слоёв:

```text
app → views → widgets → features → entities → shared
```

Стрелки задают порядок, а не обязательную цепочку вызовов: верхний слой может обращаться к любому нижнему. Например, `views` напрямую использует `shared`, `features` и `entities`; `app` подключает `entities/workspace` и `widgets/app-shell`.

При статической проверке 82 локальных импортов/реэкспортов в `portfolio` и 188 в `wehicle-demo` обратных зависимостей между этими слоями не обнаружено. Проверялись строковые пути `@/…` и относительные пути в `.ts`/`.tsx`; это проверка исходников, не результат специализированного FSD-линтера.

- Нижний слой не импортирует верхний: `shared` не знает об `entities`, а `entities` — о `features` и `views`.
- Внутри слайса можно связывать его `ui`, `model` и `lib`.
- Прямые связи разных слайсов одного слоя в обычном коде не используются. Найденное исключение — явно оформленные межсущностные связи через `@x`.
- Совместное использование двух фич организуется в вызывающем экране или виджете; в изученном коде нет импорта одной фичи из другой.

### Явные связи сущностей через `@x`

В `wehicle-demo` слайс `entities/workspace` собирает данные нескольких сущностей. Для этого каждая сущность открывает отдельный файл для потребителя:

```text
entities/
├── booking/
│   ├── model/mock.ts
│   └── @x/workspace.ts
└── workspace/
    └── model/provider.tsx
```

```ts
// entities/booking/@x/workspace.ts
export * from "../model/mock";

// entities/workspace/model/provider.tsx
import { bookingMock, type Booking } from "@/entities/booking/@x/workspace";
```

Аналогичные точки входа есть у `client`, `service`, `team` и `workshop`. Это подтверждённый паттерн **одного проекта**. Не создавать `@x` у каждой сущности заранее. При воспроизведении такой связи имя файла обозначает конкретного потребителя.

Источник: [workspace provider и его импорты](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/src/entities/workspace/model/provider.tsx).

## 4. Сегменты и размещение файлов

Используемые сегменты:

- `ui` — компоненты и их стили.
- `model` — данные, типы, состояние и предметные вычисления.
- `lib` — вспомогательная логика и хуки.
- `config` — общая конфигурация; в `portfolio` это `shared/config`.
- `styles` — глобальные и общие стили; расположение различается между проектами.

Нет требования создавать все сегменты в каждом слайсе. Например, `entities/service` в `portfolio` содержит только модель, а `features/copy-email` — UI со своей локальной логикой. Пустые `api`, `model` или `lib` для симметрии не нужны.

В `portfolio` применяется отдельная папка компонента:

```text
widgets/projects/
└── ui/
    └── projects/
        ├── projects.tsx
        └── projects.module.scss
```

В `wehicle-demo` часто используется более плоский вариант:

```text
widgets/app-shell/
├── model/navigation.ts
└── ui/
    ├── shell.tsx
    ├── shell.module.scss
    ├── header.tsx
    ├── sidebar.tsx
    └── sidebar.module.scss
```

**Рекомендация для нового сайта:** взять структуру `portfolio` с папкой на компонент. В существующем проекте сохранять принятый локальный вариант. Обязательная дополнительная вложенность не является общим правилом двух репозиториев.

## 5. Импорты и экспорты

**Общие наблюдения:**

- Алиас `@/*` указывает на `src/*`.
- Между модулями используются прямые импорты конкретных файлов.
- Внутри слайса часто используются относительные импорты модели и соседнего SCSS-модуля.
- Ни в одном из двух `src` нет `index.ts` или `index.tsx`.
- Типы импортируются через `import type` либо `type` внутри именованного импорта.

```ts
import { ProjectCard } from "@/entities/project/ui/project-card/project-card";
import { projects } from "@/entities/project/model/projects";
import type { Project } from "../../model/projects";
import styles from "./project-card.module.scss";
```

Не вводить обязательные barrel-файлы и импорты вида `@/entities/project` под видом существующего авторского соглашения. Фактический стиль — прямые пути; специальный `@x` используется для обозначенной межсущностной связи.

Экспорты зависят от проекта:

| Контекст | Наблюдаемый стиль |
| --- | --- |
| Компоненты, фичи и виджеты `portfolio` | Именованные `export function …` |
| Страницы `views` в `wehicle-demo` | Обычно `export default function …` |
| Фичи и виджеты `wehicle-demo` | Именованные экспорты встречаются регулярно |
| Файлы маршрутов Next.js | `default`-экспорт компонента или реэкспорт страницы |

Единого правила «везде только named export» в репозиториях нет. Фиксированного порядка групп импортов тоже не видно — не приписывать его авторскому стилю.

Источники: [Projects](https://github.com/chishkin-afk/portfolio/blob/efd62dddb8776423ec05452e61ac88c3beb9d520/src/widgets/projects/ui/projects/projects.tsx), [маршрут Bookings](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/src/app/dashboard/bookings/page.tsx).

## 6. Разделение Next.js и содержимого страницы

В `wehicle-demo` маршрут часто представляет собой одну строку:

```tsx
export { default } from "@/views/bookings/ui/bookings";
```

Layout подключает оболочку из `widgets`, а корневой layout — провайдер состояния из `entities/workspace`.

В `portfolio` файл маршрута может быть длиннее: он содержит metadata, JSON-LD или подготовку данных маршрута, а интерфейс передаёт компоненту из `views`. «Тонкий app» здесь означает отсутствие основной разметки экрана, а не запрет на SEO и логику маршрута.

Главная страница `portfolio` собирается из `Header`, `Hero`, `Features`, `Projects`, `Timeline`, `Questions`, `Contact`, `Footer`. Это характерная композиция законченных блоков.

При этом правило «вся логика должна быть вынесена из views» кодом не подтверждается: экраны `wehicle-demo` содержат фильтрацию, локальное состояние и обработчики; отдельные файлы достигают нескольких сотен строк. Не создавать искусственные widgets и features ради уменьшения числа строк. Выделять модуль по самостоятельной ответственности или повторному использованию.

Источники: [HomePage](https://github.com/chishkin-afk/portfolio/blob/efd62dddb8776423ec05452e61ac88c3beb9d520/src/views/home/ui/home-page/home-page.tsx), [главный маршрут portfolio](https://github.com/chishkin-afk/portfolio/blob/efd62dddb8776423ec05452e61ac88c3beb9d520/src/app/page.tsx), [экран Bookings](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/src/views/bookings/ui/bookings.tsx).

## 7. Модели, данные и состояние

1. **Контентные массивы выносятся в `model` владельца.** Проекты — в `entities/project/model/projects.ts`; варианты оценки — в `features/project-estimate/model/estimates.ts`; вопросы главной — в `views/home/model/questions.ts`.
2. **Не все данные обязаны быть entities.** Данные конкретной секции могут оставаться в `widgets/<slice>/model`, как `widgets/features/model/services.ts`.
3. **Типы могут жить рядом с данными.** В `portfolio` тип `Project` выводится из массива `as const`; в `wehicle-demo` интерфейсы и union-типы соседствуют с моками в `model/mock.ts`. Отдельный `types.ts` не обязателен.
4. **Локальное состояние остаётся рядом с UI.** `CopyEmailButton` и `ProjectEstimate` используют React hooks непосредственно в компонентах.
5. **Самостоятельные предметные расчёты выделяются в модель.** Проверка доступности времени записи находится в `features/booking/model/availability.ts` и получает данные аргументами.
6. **Специфичный хук принадлежит своему слайсу.** `useHeroParallax` лежит в `widgets/hero/lib`, общий `useQueryState` — в `shared/lib`.

В `wehicle-demo` общее состояние хранится в React Context (`DemoProvider` + `useDemo`), включает данные и setters нескольких сущностей и подключается в корневом layout. Часть состояния экрана, например выбранный вид и запись, синхронизируется с query-параметрами через `useQueryState`.

Это устройство **демонстрационного приложения**, а не доказательство правила «всё состояние любого проекта должно быть в одном Context». В обоих фронтендах не используются Redux, Zustand или TanStack Query; наличие привычки к конкретной библиотеке server state по этим примерам установить нельзя. Сегментов `api` и полноценного фронтенд-слоя работы с backend в изученных снимках нет.

Источники: [модель Project](https://github.com/chishkin-afk/portfolio/blob/efd62dddb8776423ec05452e61ac88c3beb9d520/src/entities/project/model/projects.ts), [availability](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/src/features/booking/model/availability.ts), [useQueryState](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/src/shared/lib/use-query-state.ts).

## 8. Компоненты и TypeScript

- Использовать TypeScript со `strict: true`; это включено в обоих проектах.
- Имена компонентов и типов — `PascalCase`; файлов и каталогов — `kebab-case`; хуков — `useSomething` при имени файла `use-something.ts`.
- Основная форма компонентов — обычные функции. Короткие props часто типизированы прямо в сигнатуре.
- Для более сложных контрактов подходят отдельные `type`/`interface`. В коде есть оба варианта, запрета на один из них нет.
- Для UI-обёрток используются стандартные React-типы, например `ComponentProps<"a">` и `ComponentProps<typeof NextLink>`.
- Локальные вспомогательные компоненты могут находиться в том же файле: например, `BookingForm` рядом с `BookingDialog`.
- Добавлять `"use client"` там, где нужны hooks, события или browser API. В `portfolio` явно помечены 5 из 35 TS/TSX-файлов, в интерактивном `wehicle-demo` — 28 из 61. Эти числа показывают расположение директив, а не размер клиентского бандла.
- Не вводить лимит строк или обязательное разделение каждого компонента на `ui/model/lib`: такого общего соглашения не обнаружено.

## 9. Стили и общий UI

**Общее правило — SCSS Modules и CSS custom properties.** Tailwind, CSS-in-JS и готовая большая библиотека UI-компонентов в этих проектах не используются.

- Компонентные стили находятся в `.module.scss`; импорт называется `styles` в `portfolio`, часто `s` или `layout` в `wehicle-demo`.
- Используются локальные смысловые классы: `section`, `heading`, `button`, `imageWrap`, `calendarCell`.
- Цвета, поверхности, отступы и easing могут задаваться через CSS-переменные в `:root`.
- Глобальные стили отвечают за reset, типографику, focus и базовое поведение.
- В обоих проектах есть `:focus-visible` и обработка `prefers-reduced-motion`.
- Динамические значения допустимо передавать через inline styles: например, вычисляемую сетку календаря. Строгого запрета на inline styles нет.

Размещение глобальных стилей не едино: `portfolio` использует `app/styles/globals.scss`, а `wehicle-demo` — `shared/styles/globals.scss` и общие модули `screen`, `utility`, `auth`.

Общий UI тоже организован двумя способами: отдельные компоненты в `portfolio`, набор контролов в `shared/ui/controls.tsx` в `wehicle-demo`. Не требовать разбиения каждого контрола в отдельную папку при работе с уже принятым компактным набором.

## 10. Форматирование и проверки

В обоих проектах есть npm lockfile, команды `typecheck` (`tsc --noEmit`) и `build` (`next build`). Это подтверждённый базовый способ проверки изменений. В `portfolio` дополнительно есть `verify:seo`, а в `wehicle-demo` — `format`.

Явная конфигурация Prettier найдена только в `wehicle-demo`:

```json
{
  "semi": true,
  "arrowParens": "avoid",
  "tabWidth": 2,
  "trailingComma": "all",
  "jsxSingleQuote": true
}
```

В `portfolio` JSX обычно использует двойные кавычки. Поэтому JSX-кавычки и скобки одиночного аргумента стрелочной функции нельзя считать универсальным соглашением автора.

В обоих фронтендах не обнаружена настроенная проверка FSD-границ через ESLint/Steiger или отдельная команда тестов. Не описывать их как уже обязательные инструменты автора. Для изменений кода разумно сохранять существующие `typecheck` и `build`; специализированные проверки применять по задаче и конфигурации проекта. Во время этого анализа сборки не запускались: код не менялся, задача состояла в исследовании структуры.

Источники: [package.json portfolio](https://github.com/chishkin-afk/portfolio/blob/efd62dddb8776423ec05452e61ac88c3beb9d520/package.json), [package.json wehicle-demo](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/package.json), [.prettierrc](https://github.com/chishkin-afk/wehicle-demo/blob/a482de44c0eb4e4d4c5e8ec32bdff77c90df545b/.prettierrc).

## 11. Что не следует выдавать за авторское правило

| Неподтверждённое требование | Что видно в репозиториях |
| --- | --- |
| Каждый слайс обязан иметь публичный `index.ts` | Используются прямые пути, index-файлов нет |
| Все страницы должны быть в `pages` | Используется `views` вместе с Next.js `app` |
| В `views` допустима только композиция | В демо там также состояние и логика экрана |
| Каждая сущность должна иметь `api`, `model`, `ui`, `lib` | Создаются только нужные сегменты |
| Все компоненты должны иметь одинаковую глубину каталогов | У `portfolio` и `wehicle-demo` разные варианты |
| Только named exports, только один вид кавычек | Соглашения отличаются по проектам |
| Всегда нужен единый глобальный store | Context найден в демо, портфолио использует локальные состояния |
| Нужно заранее подключать библиотеку форм, запросов или состояния | По изученному коду такой стандарт не установлен |

Отдельно: Go-проекты подтверждают интерес к разделению предметной логики и инфраструктуры, но их Clean Architecture не следует механически переносить во фронтенд. В `posted` есть `internal/domain`, `application`, `infrastructure`; в `todo` слои вложены в `internal/modules/auth` и `internal/modules/task`. Это другой архитектурный контекст, не дополнительные слои FSD.

## 12. Порядок добавления новой функциональности

Следующий порядок — практическое обобщение наблюдаемого стиля для дальнейшей разработки:

1. Определить владельца: страница, виджет, пользовательский сценарий, сущность или общий код.
2. Создать только необходимые сегменты внутри соответствующего слайса.
3. Данные и расчёты держать рядом с владельцем; переносить в `entities` или `shared` при появлении подходящей ответственности.
4. Импортировать конкретные файлы через `@/…`, а близкие внутренние зависимости — относительно текущего файла.
5. Сохранять направление зависимостей вниз; редкие межсущностные связи оформлять явно по примеру `@x/<consumer>`.
6. Собирать страницу в `views`, подключать её из Next.js `app`.
7. Стили держать в SCSS Modules, общие значения — в существующих CSS-переменных.
8. Сохранять соглашения выбранного проекта по вложенности, экспортам и форматированию.
9. Проверять изменения штатными командами проекта; не добавлять архитектурные инструменты и зависимости только ради соответствия чужому шаблону FSD.
